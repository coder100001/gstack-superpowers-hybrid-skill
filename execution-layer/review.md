# Code Review Rules

> **层**: Execution Layer · **职责**: 质量把关
> **前置条件**: 测试已通过（见 testing.md）
> **禁止**: 跳过审查、流于形式、个人偏好主导

---

## 1. 审查清单

### 1.1 上下文契约对照
- [ ] 是否遵循架构决策记录（ADR）
- [ ] 是否遵守领域边界约定
- [ ] 是否符合项目约束规范
- [ ] 是否保持与已有代码风格一致
- [ ] 是否引入未经批准的依赖

### 1.2 代码质量检查
- [ ] 命名清晰、语义明确
- [ ] 函数/类职责单一
- [ ] 无过度复杂的逻辑（圈复杂度 < 10）
- [ ] 错误处理完善
- [ ] 无重复代码（DRY 原则）
- [ ] 注释恰当（无无用注释）

### 1.3 测试覆盖验证
- [ ] 新代码有对应的测试
- [ ] 测试覆盖了主要路径
- [ ] 测试覆盖了错误路径
- [ ] 测试清晰易读
- [ ] 测试可独立运行

### 1.4 架构合规性
- [ ] 模块划分合理
- [ ] 依赖关系清晰
- [ ] 无循环依赖
- [ ] 符合分层架构要求
- [ ] 配置外部化（无硬编码）

---

## 2. 代码质量标准

### 2.1 可读性
- 遵循现有代码风格
- 变量名见名知意
- 函数长度 < 50 行
- 文件长度 < 500 行

### 2.2 可维护性
- 低耦合、高内聚
- 依赖注入明确
- 接口设计稳定
- 变更影响可控

### 2.3 可测试性
- 依赖可 mock
- 函数无副作用（纯函数优先）
- 状态管理清晰

---

## 3. 审查流程

### 3.1 自审（Self-Review）
```
提交前必须完成：
  ├─ 对照审查清单逐项检查
  ├─ 运行 lint 和类型检查
  ├─ 确保所有测试通过
  └─ 撰写清晰的提交信息
```

### 3.2 同行审查（Peer Review）
```
PR 审查要点：
  ├─ 理解变更意图
  ├─ 验证技术方案
  ├─ 检查代码质量
  ├─ 确认测试充分
  └─ 提出建设性意见
```

### 3.3 审查通过标准
- 至少 1 人批准
- 所有评论已解决
- CI 检查全通过
- 无阻塞性问题

---

## 4. 红线

### 4.1 绝对不能合并
- ❌ 违反上下文契约
- ❌ 测试未通过
- ❌ 存在安全漏洞
- ❌ 引入未知风险
- ❌ 代码质量严重下降

### 4.2 必须整改
- ⚠️ 命名混乱
- ⚠️ 逻辑复杂度过高
- ⚠️ 缺少测试
- ⚠️ 错误处理不当
- ⚠️ 性能问题

---

## 5. 审查文化

- 对事不对人
- 提出问题同时提供建议
- 尊重不同技术观点
- 及时响应审查意见
- 持续学习和改进
