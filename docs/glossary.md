# 术语表 (Glossary)

> 本文档用一句话解释 AI Engineering Governance System 中的核心术语。

---

## 三层架构

| 术语 | 定义 |
|------|------|
| **Decision Layer（决策层）** | 负责需求澄清、架构审议、任务拆解的层级，回答"该做什么？" |
| **Context Layer（上下文层）** | 负责契约持久化、约束强制的层级，回答"共识是什么？" |
| **Execution Layer（执行层）** | 负责受约束实现、测试验证的层级，回答"如何做好？" |
| **Bridges（桥接）** | 连接各层的协议层，负责层间信息传递和转化 |
| **Governance（治理）** | 跨层规则强制机制，包括决策冻结、状态验证、变更控制 |

---

## 核心概念

| 术语 | 定义 |
|------|------|
| **Context Hydration（上下文注水）** | 在开始编码前，把项目的基本规则（如架构风格、禁止模式）明确告知 AI 的过程 |
| **Decision Freeze（决策冻结）** | 进入实现阶段后锁定架构、需求、API 契约，禁止自行修改的机制 |
| **ADR（Architecture Decision Record）** | 架构决策记录，记录重大技术决策的背景、方案、否决理由和回滚策略 |
| **Spec（规格契约）** | 项目约束的正式文档，是执行的唯一依据 |
| **Gate（门禁）** | 状态跃迁前的强制检查点，未通过则阻断流程 |

---

## 状态机

| 术语 | 定义 |
|------|------|
| **IDEA** | 任务接收状态，工作流的起点 |
| **DISCOVERY** | 需求澄清状态，通过渐进式提问理解需求 |
| **REQUIREMENT_LOCK** | 需求确认状态，用户必须明确确认需求范围 |
| **ARCH_REVIEW** | 架构审议状态，多维度评估方案可行性 |
| **TASK_DECOMPOSITION** | 任务拆解状态，将需求分解为可执行任务 |
| **IMPLEMENTATION** | 编码实现状态，执行 TDD 开发 |
| **SELF_REVIEW** | 自审状态，对照契约检查实现 |
| **QA** | 质量验证状态，执行测试和功能验证 |
| **SHIP_REVIEW** | 发布检查状态，验证交付物完整性 |
| **RETRO** | 复盘记录状态，总结经验教训 |

---

## 复杂度分级

| 术语 | 定义 |
|------|------|
| **L0（极简任务）** | 修改 1 个文件、< 10 行代码的任务，完全跳过三层架构 |
| **L1（简单任务）** | 修改 < 3 个文件、< 100 行代码的任务，简化流程 |
| **L2（中等任务）** | 修改 3-8 个文件、100-500 行代码的任务，标准流程 |
| **L3（复杂任务）** | 修改 > 8 个文件、> 500 行代码的任务，完整流程 |

---

## 审议维度

| 术语 | 定义 |
|------|------|
| **Product 维度** | 评估业务价值、用户影响、范围合理性、ROI |
| **Architect 维度** | 评估模块划分、依赖方向、技术选型 |
| **Performance 维度** | 评估吞吐、延迟、缓存策略、潜在瓶颈 |
| **Security 维度** | 评估信任边界、数据暴露、认证授权 |
| **Operations 维度** | 评估部署复杂度、回滚可行性、监控覆盖 |

---

## 强制规则

| 术语 | 定义 |
|------|------|
| **HARD-GATE** | 强制阻断点，未满足条件则禁止进入下一状态 |
| **STATUS-BAR** | 状态栏规则，要求 AI 每次响应必须显示当前状态 |
| **强制引述** | 上下文注水时必须引述具体约束条款，而非仅声明"已加载" |
