# 03a - Step 0 + Phase 0.5a/0.5b + Phase 0.6

## Step 0: 复杂度评估

**触发条件**: 任何任务开始前

### 评估步骤

1. **统计变更范围**
   - 列出所有需要新增、修改、删除的文件
   - 预估每处变更的代码行数
   - 识别哪些文件属于核心业务逻辑

2. **识别架构影响**
   - 是否修改接口定义？
   - 是否影响数据流？
   - 是否涉及配置变更？
   - 是否需要更新文档？

3. **评估风险等级**
   - 是否涉及数据迁移？
   - 是否影响现有用户？
   - 是否可回滚？
   - 是否有外部依赖？

4. **确定复杂度级别**
   - 根据判定标准确定 L1/L2/L3
   - 记录评估理由
   - 告知用户评估结果

### 输出要求

必须输出《复杂度评估报告》，包含：
- 变更文件清单
- 预估代码行数
- 影响分析
- 复杂度级别判定
- 建议的流程路径

## Phase 0.5: 需求澄清 + 方案设计

**触发条件**: L2+ 任务 (L1 可选)

### 目标

先通过 brainstorming 方法论澄清需求、产出设计方案，再编写 Design Doc 存档。

### 子流程

```
┌──────────────────────────────────────────┐
│  Phase 0.5a: 需求澄清 (brainstorming)    │
│  渐进式提问 → 方案探索 → 设计呈现         │

                    ↓ 用户确认设计
┌──────────────────────────────────────────┐
│  Phase 0.5b: Design Doc 编写              │

                    ↓
              Phase 0.6 (方案审核确认)
```

### Phase 0.5a: 需求澄清 (调用 brainstorming skill)

> 此阶段必须完整执行 brainstorming 技能的方法论。不只是在脑子里过一遍——要真正用 brainstorming 的流程与用户交互。

#### Step 0: Announce at Start

在需求澄清开始时，必须声明：

> "我将使用 brainstorming 技能进行需求澄清。我会先探索项目上下文，然后通过渐进式提问理解需求，最后提出设计方案供你审查。"

#### Step 1: 探索项目上下文

在任何提问之前，必须先理解项目现状：
- 检查项目目录结构、关键配置文件
- 阅读相关代码文件（了解现有架构和数据流）
- 检查最近的 git 提交记录
- 了解当前的技术栈和约束

#### Step 2: 范围评估与子系统拆解

在开始渐进式提问之前，判断需求规模。**此阶段漏检多子系统将导致 Phase 1 回退，浪费 Design Doc 和方案确认的工作。**

**多子系统判定标准** (满足任意 2 项即为多子系统):

| 维度 | 判定标准 |
|------|---------|
| **独立数据模型** | 有独立的数据库表/实体集合，可独立 CRUD |
| **独立用户界面** | 有独立的页面/路由/入口点 |
| **独立部署单元** | 可独立部署、独立扩缩容、独立监控 |
| **独立用户角色** | 不同子系统由不同角色使用 |
| **独立外部依赖** | 依赖不同的第三方服务或 API |

**处理规则**:
- 满足任意 2 项 → **立刻标记为多子系统**
- 与用户确认拆解方案：每个子系统独立走 brainstorming → Design Doc → Plan 周期
- 子系统之间通过明确接口契约通信，在各自的 spec/plan 中只定义接口、不实现对方

**单一子系统判定**: 所有功能围绕同一个核心数据模型/业务流程，即使涉及多个文件也视为单一子系统。

#### Step 3: 渐进式需求澄清

**核心原则** (来自 brainstorming 方法论):

| 原则 | 说明 |
|------|------|
| 一次只问一个问题 | 不堆砌问题，避免用户被淹没 |
| 优先选择题 | 给 2-4 个选项降低用户回答成本；开放问题也可以 |
| 一条消息一个问题 | 话题需要深入时拆成多个问题 |
| 必要时回溯澄清 | 如果发现矛盾或模糊，返回确认 |
| 聚焦目的/约束/成功标准 | 理解 what & why，而不是 how |

**澄清维度参考** (按优先级递进，不是强制清单):

| 轮次 | 维度 | 说明 |
|:----:|------|------|
| 1 | **目的与痛点** | 这个功能的核心目标是什么？解决什么具体痛点？ |
| 2 | **用户与角色** | 谁会使用？有几种角色？每种角色有什么不同需求？ |
| 3 | **约束条件** | 技术栈限制？兼容性要求？时间/资源约束？ |
| 4 | **成功标准** | 怎么判断做好了？有具体可衡量指标吗？ |
| 5 | **边界与范围** | 有什么明确不做的事情？范围的硬边界在哪里？ |
| 6 | **风险识别** | 有哪些你担心的潜在问题或不确定性？ |

**注意**: 以上是参考维度而非强制清单。根据实际对话灵活调整，目标是真正理解需求，不是跑完清单。

**涉及视觉的问题**: 当需要澄清任何可见的事物（UI 布局、组件外观、交互形态）时，可使用浏览器工具展示参考或原型帮助沟通。

#### Step 4: 方案探索

理解需求后，提出 2-3 个可选方案：
- 以对话方式呈现，带利弊分析
- 先给出推荐方案及理由
- 解释为什么推荐这个方案

#### Step 5: 设计呈现

确认方案方向后，呈现具体设计：
- 按章节逐步呈现，每个章节后确认是否正确
- 覆盖：架构、组件/模块、数据流、错误处理、测试策略
- 愿意回溯澄清，如果某些部分不合理

#### 设计隔离性原则

对每个设计单元，回答三个问题：
1. 它做什么？（单一清晰目的）
2. 怎么使用它？（良好定义的接口）
3. 它依赖什么？（明确的依赖边界）

小文件是好的信号——当文件变大时，通常意味着它承担了太多职责。

#### 已有代码库的特殊处理

- 先探索当前代码结构，再提出变更
- 遵循现有模式
- 如果已有代码存在问题影响当前工作（如文件太大、边界不清、职责混乱），在设计中有针对性地改进
- 不要提出无关的重构——聚焦于服务于当前目标

#### Step 6: 反模式警告

| 反模式 | 为什么是问题 |
|--------|-------------|
| **"太简单不需要设计"** | 最简单项目的未检验假设浪费最多工作。设计可以很短（简单项目几句话），但必须呈现并获批准 |
| **跳过上下文探索** | 不理解项目现状的提问是盲目的 |
| **一次性堆砌问题** | 用户被淹没，回答质量下降 |
| **假设需求** | 没有确认过的假设 = 潜在的返工 |
| **只提一个方案** | 没有对比就没有真正的选择 |

#### Step 7: 保存 Spec 并过渡到 Design Doc

用户确认设计后：
1. 将确认的设计保存为 spec 文件到 `specs/YYYY-MM-DD-<feature>-spec.md`
2. 让用户审查 spec 文件
3. 用户批准 spec 后，进入 Phase 0.5b 编写 Design Doc

**过渡协议**: 需求澄清完成后，只应建议进入 Design Doc 编写（Phase 0.5b），不直接跳转到编码实现。

### Phase 0.5b: Design Doc 编写

**前置**: Phase 0.5a 的 spec 文件已保存到 `specs/YYYY-MM-DD-<feature>-spec.md` 并获用户批准。

> Design Doc 类似 DB Migrations — 记录重大设计决策的思考过程。spec 回答 "what"，Design Doc 回答 "how and why"。

#### Spec 自审查

写完 Design Doc 后，AI 必须自审查：

1. **占位符扫描**: 有没有 "TBD"、"TODO"、不完整的部分？模糊的需求？→ 修复
2. **内部一致性**: 各章节是否矛盾？架构描述是否与功能描述一致？
3. **范围检查**: 是否聚焦在单个实现计划内？还是需要进一步拆解？
4. **歧义检查**: 任何需求是否可被两种方式解读？若是，选一个并显式化

发现问题 → 立即修复 → 无需重复审查。

#### 方案调研

**调研维度**:
- 业界最佳实践
- 类似项目的实现方式
- 技术选型的优缺点
- 潜在的坑和解决方案

#### 方案对比

**必须对比至少 2-3 个方案**:

| 方案 | 优点 | 缺点 | 适用场景 | 复杂度 |
|------|------|------|---------|--------|
| A | ... | ... | ... | L? |
| B | ... | ... | ... | L? |
| C | ... | ... | ... | L? |

#### 设计决策

**决策依据**:
- 为什么选这个方案？
- 放弃了什么？为什么？
- 未来的扩展性如何？
- 维护成本如何？

```markdown

`docs/design-docs/001-feature-name.md`

## 背景与问题
[描述要解决什么问题]

## 目标

- [ ] 目标2

## 方案对比

### 方案 A: [名称]
**优点**:
- ...

**缺点**:
- ...

### 方案 B: [名称]

## 详细设计

|------|------|------|---------|
| ... | 高/中/低 | 高/中/低 | ... |

## 验收标准
- [ ] 标准1
```

## Phase 0.6: 方案审核确认 (NEW!)

**触发条件**: 所有级别任务 (L1/L2/L3)

<HARD-GATE>
**这是强制阻断点！** 用户必须明确确认方案选择，AI 才能继续。
</HARD-GATE>

### 目标

在 Design Doc 完成后、Plan 创建前，确保用户对方案有充分理解并明确选择。

### 必须展示的内容

1. **方案对比表格**
   - 至少 2-3 个可选方案
   - 清晰的优缺点对比
   - 复杂度评估

2. **AI 推荐方案**
   - 明确推荐哪个方案
   - 详细的推荐理由
   - 风险提示

3. **用户确认**
   - 等待用户明确回复
   - 不能默认选择
   - 不能跳过

### 确认对话模板

```
AI: 基于需求分析，我提出了以下方案：

【方案对比表】

我推荐采用【方案 X】，理由：
1. ...
2. ...

⚠️ 风险提示：...

请确认：
1. 您是否同意选择【方案 X】？
2. 或者您倾向于其他方案？
3. 是否有其他考虑因素？

[等待用户明确回复]
```

### 阻断规则

- ❌ 用户未回复 → 等待
- ❌ 用户回复模糊 → 追问澄清
- ❌ 用户选择不同方案 → 重新评估影响
- ✅ 用户明确确认 → 继续 Phase 1

### 输出要求

必须记录：
- 用户选择的方案
- 选择理由
- 确认时间
- 相关风险接受声明
