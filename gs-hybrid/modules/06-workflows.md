# 06 - 专用流程指令

## 指令概览

| 指令 | 功能 | 适用场景 |
|------|------|---------|
| `/plan` | 规划流程 | 新功能开发前的完整规划 |
| `/review` | 代码审查 | 代码完成后的质量审查 |
| `/test` | 测试驱动 | TDD 开发流程 |
| `/ship` | 发布准备 | 提交前的最终检查 |
| `/qa` | 质量保证 | 功能完成后的验证 |
| `/debug` | 调试助手 | 问题诊断与修复 |
| `/refactor` | 重构建议 | 代码改进与优化 |

---

## /plan - 规划流程

### 触发方式

```
用户: /plan 我要开发一个新功能
或
用户: hybrid plan 开发用户认证模块
```

### 执行流程

```
Step 0 → Phase 0.5 → Phase 0.6 → Phase 1 → Phase 1.5
```

### 输出

- 复杂度评估报告
- Design Doc (L2+)
- PLAN.md
- 用户确认记录

## /review - 代码审查

### 触发方式

```
用户: /review 请审查这段代码
或
用户: hybrid review [文件路径]
```

### 执行流程

```
Phase 2 → Phase 3 → Phase 4 (L3) → Phase 5 (L3)
```

### 审查维度

1. **工程规范** - 代码风格、最佳实践
2. **架构设计** - SOLID 原则、模块职责
3. **测试覆盖** - 测试策略、边界条件
4. **安全扫描** - 漏洞检测、敏感信息

### 输出

- 工程规范检查报告
- 架构评审报告
- QA 评审报告 (L3)
- 安全评审报告 (L3)

## /debug - 调试助手

### 触发方式

```
用户: /debug 这个 bug 怎么解决
或
用户: hybrid debug [问题描述]
```

### 执行流程

```
Bug 分级 → D1 Symptom Lock → D2 Root Cause → D3 Pattern → D4 Fix → D5 Verify
```

### Bug 分级标准

| 级别 | 判定标准 | 预计时间 | 路径 |
|------|---------|---------|------|
| **Quick** | 单文件、明显错误、可本地复现 | 15-30min | D1 → D4 → Verify |
| **Standard** | 跨文件但范围明确、有错误信息 | 1-2h | 完整 5 阶段 |
| **Deep** | 间歇性、架构级、无明确错误 | 2h+ | 完整 5 阶段 + Arch Review |

**分级规则** (满足任一即升级):
- 涉及 3+ 个文件 → Standard
- 无错误信息或间歇性 → Deep
- 近期同一区域重复出现 → Deep

### 5 阶段详解

#### D1: Symptom Lock

**目标**: 标准化问题定义，锁定调查范围

1. **问题定义** (使用标准模板)
   ```
   BUG REPORT
   ════════════════════════════════════════
   Symptom:      [用户观察到的现象]
   Reproduce:    [复现步骤]
   Expected:     [期望行为]
   Actual:       [实际行为]
   Environment:  [版本、配置、分支]
   First seen:   [首次出现时间]
   ════════════════════════════════════════
   ```

2. **Scope Lock** (GStack)
   - 识别最窄的影响目录
   - 写入 freeze-dir.txt
   - 防止调试范围蔓延

3. **历史学习查询** (GStack)
   - 搜索 prior investigations
   - 搜索 project learnings
   - 若发现相关历史，应用并标注

**输出**: Bug Report + Scope Lock + 历史学习摘要

#### D2: Root Cause Investigation

**目标**: 找到根因，不是症状

1. **读错误信息** — 不跳过任何警告
2. **复现** — 确定性复现是继续的前提
3. **检查近期变更** — `git log --oneline -20 -- <affected-files>`
4. **追溯数据流** — 从症状反向追踪到源头
5. **多组件系统** — 每层边界加诊断日志

**铁律**: 未完成 D2，不能进入 D4

**输出**: Root Cause Hypothesis (具体、可验证的声明)

#### D3: Pattern Analysis

**目标**: 匹配已知模式，避免重复造轮子

1. **匹配已知模式**
   | 模式 | 特征 | 检查点 |
   |------|------|--------|
   | 竞态条件 | 间歇性、时间相关 | 共享状态并发访问 |
   | 空值传播 | NoMethodError、TypeError | 可选值缺少守卫 |
   | 状态损坏 | 数据不一致 | 事务、回调、钩子 |
   | 集成失败 | 超时、意外响应 | 外部 API、服务边界 |
   | 配置漂移 | 本地正常、线上失败 | 环境变量、feature flags |
   | 缓存过期 | 旧数据、清除后恢复 | Redis、CDN、浏览器缓存 |

2. **外部搜索** — 若模式不明，搜索 "{framework} {sanitized error}"
3. **检查 TODOS.md** — 已知问题列表
4. **检查 git log** — 同一区域的历史修复

**输出**: 匹配的模式 + 差异分析

#### D4: Hypothesis & Fix

**目标**: 验证假设，修复根因

1. **确认假设** — 添加临时日志/断言，运行复现
2. **假设错误** — 返回 D2 收集更多证据
3. **3-strike 规则** — 3 次假设失败 → STOP，质疑架构
4. **修复根因** — 最小 diff，不碰相邻代码
5. **回归测试** — 必须先失败、再通过的测试
6. **全量测试** — 确保无回归

**输出**: 修复代码 + 回归测试 + 测试报告

#### D5: Verification & Report

**目标**: 验证修复，记录学习

1. **复现验证** — 原始场景确认修复
2. **全量测试** — 粘贴输出
3. **结构化报告**
   ```
   DEBUG REPORT
   ════════════════════════════════════════
   Symptom:         [用户观察到的现象]
   Root cause:      [实际错误]
   Fix:             [修改内容，含 file:line]
   Evidence:        [测试输出]
   Regression test: [file:line]
   Related:         [TODOS.md 项、历史 bug、架构备注]
   Status:          DONE | DONE_WITH_CONCERNS | BLOCKED
   ════════════════════════════════════════
   ```
4. **记录学习** — `gstack-learnings-log` (非显而易见模式)

**输出**: Debug Report + 学习记录

### 调用的 Skills

- `systematic-debugging-v2` — 统一调试流程 (融合 Superpowers + GStack)
- `/qa` — 修复验证 (GStack)

### 输出

- Bug Report
- Root Cause Hypothesis
- Debug Report
- 回归测试
- 学习记录

### 快速修复流程

```
用户: /debug 快速修复 [问题]

AI: 评估为 Quick 级别 → 跳过 D2/D3 → 直接定位修复 → 本地验证 → 完成
```

### 异常处理

| 场景 | 处理 |
|------|------|
| 3+ 假设失败 | STOP，质疑架构，AskUserQuestion |
| 修复涉及 >5 文件 | AskUserQuestion 确认 blast radius |
| 无法复现 | 添加日志，标记 DONE_WITH_CONCERNS |
| 同一区域重复 bug | 升级为 Deep，触发架构评审 |

## /refactor - 重构建议

### 触发方式

```
用户: /refactor 这段代码可以优化吗
或
用户: hybrid refactor [代码范围]
```

### 执行流程

```
代码分析 → 识别坏味道 → 提出方案 → 用户确认 → 执行重构 → 验证
```

### 重构类型

1. **提取函数** - 过长函数拆分
2. **合并重复** - 消除重复代码
3. **重命名** - 提高可读性
4. **简化条件** - 简化复杂逻辑
5. **引入设计模式** - 改善架构

### 输出

- 代码分析报告
- 重构建议
- 重构后的代码
- 验证结果
