# 04a - Phase 2-3: 工程规范与架构评审

## Phase 2: 工程规范设计

**触发条件**: L2+ 任务 (L1 可选)

**调用 Skill**: `requesting-code-review` (规范检查模式)

### 目标

确保代码符合项目工程规范，包括代码风格、最佳实践、性能要求等。

### 检查清单

#### 2.1 代码风格检查

- [ ] **命名规范**
  - 变量名是否符合项目约定
  - 函数名是否清晰表达意图
  - 常量是否使用正确的命名方式

- [ ] **代码格式**
  - 缩进是否一致
  - 行长度是否符合限制
  - 空行使用是否恰当

- [ ] **注释规范**
  - 公共函数是否有文档注释
  - 复杂逻辑是否有解释
  - TODO/FIXME 是否标记清楚

#### 2.2 最佳实践检查

- [ ] **错误处理**
  - 所有错误是否被处理
  - 错误信息是否有用
  - 是否有 panic/recover 滥用

- [ ] **资源管理**
  - 文件句柄是否正确关闭
  - 数据库连接是否正确释放
  - 是否有资源泄漏风险

- [ ] **并发安全**
  - 共享状态是否正确保护
  - 是否有竞态条件
  - 死锁风险是否被评估

#### 2.3 性能要求

- [ ] **算法复杂度**
  - 时间复杂度是否合理
  - 空间复杂度是否合理
  - 是否有明显的性能瓶颈

- [ ] **资源使用**
  - 内存使用是否合理
  - CPU 使用是否合理
  - 是否有不必要的分配

### 输出要求

生成《工程规范检查报告》：

```markdown
# 工程规范检查报告

## 检查项

### 代码风格
- [ ] 命名规范
- [ ] 代码格式
- [ ] 注释规范

### 最佳实践
- [ ] 错误处理
- [ ] 资源管理
- [ ] 并发安全

### 性能要求
- [ ] 算法复杂度
- [ ] 资源使用

## 检查结果

| 检查项 | 状态 | 问题 | 建议 |
|--------|------|------|------|
| ... | ✅/⚠️/❌ | ... | ... |

## 整改清单

- [ ] 问题 1: ...
- [ ] 问题 2: ...
```

## Phase 3: 架构师评审

**触发条件**: L2+ 任务 (L1 可选)

**调用 Skill**: `requesting-code-review` (架构评审模式)

### 目标

从架构角度审查设计，确保符合 SOLID 原则和设计模式。

### SOLID 原则检查

#### S - 单一职责原则 (Single Responsibility)

- [ ] 每个模块/类是否只有一个改变的理由？
- [ ] 函数是否只做一件事？
- [ ] 是否存在 God Class/Object？

#### O - 开闭原则 (Open/Closed)

- [ ] 是否对扩展开放？
- [ ] 是否对修改关闭？
- [ ] 新增功能是否需要修改现有代码？

#### L - 里氏替换原则 (Liskov Substitution)

- [ ] 子类是否可以替换父类？
- [ ] 继承关系是否合理？
- [ ] 是否存在违反契约的行为？

#### I - 接口隔离原则 (Interface Segregation)

- [ ] 接口是否小而专注？
- [ ] 客户端是否依赖不需要的方法？
- [ ] 是否存在胖接口？

#### D - 依赖倒置原则 (Dependency Inversion)

- [ ] 是否依赖抽象而非具体？
- [ ] 高层模块是否依赖低层模块？
- [ ] 依赖关系是否正确？

### 架构检查清单

#### 模块职责
- [ ] 模块边界是否清晰？
- [ ] 模块间耦合是否合理？
- [ ] 内聚性是否高？

#### 接口设计
- [ ] 接口是否稳定？
- [ ] 参数设计是否合理？
- [ ] 返回值是否一致？

#### 数据流
- [ ] 数据流向是否清晰？
- [ ] 状态管理是否合理？
- [ ] 是否有循环依赖？

#### 扩展性
- [ ] 是否容易添加新功能？
- [ ] 是否容易替换实现？
- [ ] 是否支持未来需求？

## 评审异常处理

### 发现问题时的处理流程

```
发现问题 → 记录问题 → 评估影响 → 提出方案 → 用户决策
```

### 问题分级

| 级别 | 定义 | 处理方式 |
|------|------|---------|
| **阻断性** | 必须修复，否则不能继续 | 立即修复 |
| **严重性** | 影响功能或安全，建议修复 | 协商修复 |
| **一般性** | 代码质量问题，可以后续优化 | 记录待办 |
| **建议性** | 改进建议，不强制 | 可选采纳 |

### 用户决策选项

当发现问题时，给用户以下选项：

1. **立即修复** - 暂停当前流程，先修复问题
2. **继续但记录** - 继续当前流程，但记录技术债务
3. **接受风险** - 明确接受风险，继续执行
4. **重新设计** - 问题太大，需要回到设计阶段
