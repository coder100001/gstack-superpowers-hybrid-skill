## 项目配置 (开始前必读)

**使用本 Skill 前，必须根据当前项目填充以下配置。** 所有 `{{KEY}}` 占位符将替换为下方对应值。若配置缺失，流程将阻断并提示补充。

| 配置项 | 说明 | 示例 (Go 项目) |
|-------|------|---------------|
| `LANGUAGE` | 主要开发语言 | `Go 1.21+` |
| `TEST_COMMAND` | 运行全量测试的命令 | `go test ./... -race` |
| `COVERAGE_COMMAND` | 生成覆盖率报告的命令 | `go test ./... -coverprofile=coverage.out` |
| `BENCH_COMMAND` | 运行性能基准的命令 | `go test -bench=. -benchmem ./...` |
| `LINT_COMMAND` | 代码静态检查命令 | `golangci-lint run` |
| `SECURITY_SCANNER` | 安全漏洞扫描命令 | `gosec ./...` |
| `CODE_REVIEW_GUIDE` | 官方代码审查指南链接 | `https://github.com/golang/go/wiki/CodeReviewComments` |
| `CONCURRENCY_MODEL` | 并发模型说明（用于泄漏检查） | `goroutine` |
| `INJECTION_PATTERNS` | 常见注入模式（日志/查询等） | `fmt.Sprintf.*%s.*query`, `exec.Command.*input` |
| `SECRET_PATTERNS` | 敏感信息检测模式 | `password\\s*=\\s*[\"'][^\"']*[\"']` |

**自定义扩展**
如需绑定特殊项目规则（如内部框架、私有依赖白名单），请直接修改对应 Phase 的检查清单，或新增自定义 Phase 并通过复杂度矩阵引入。

## 核心概念定义

| 概念 | 定义 |
|-----|------|
| **Design Doc** | 编号设计文档，存储在 `design-docs/` 目录，记录重大功能/改动的调研、设计决策和演进理由，类似 DB Migrations 记录项目思考进化脉络 |
| **方案审核确认** | 在 Design Doc 完成后、Plan 创建前，AI 必须展示多个可选方案对比，由用户确认选择哪个方案 |
| **Plan验证确认** | 在 Plan 完成后、编码开始前，AI 必须进行范围、风险、验收标准的验证，由用户确认开始执行 |
| **变更文件数** | 新增、修改、删除的文件总数（不含自动生成文件） |
| **新增代码行** | 不含空行和注释的净增代码行数 |
| **架构影响** | 涉及模块间接口、数据流、部署方式的变更 |
| **风险等级** | 低：仅影响非核心功能；中：影响核心功能但可回滚；高：涉及数据迁移或不可逆变更 |
| **接口变更** | 对已有公共 API 的签名、参数、返回值的修改 |
| **依赖变更** | 新增或替换项目依赖管理器（如 go.mod）中的外部依赖 |

## 任务复杂度分级

根据变更范围、影响面和风险等级，将任务分为三级：

### L1 - 简单任务 (轻量级流程)
**判定标准** (满足任一):
- 修改文件 < 3 个
- 新增代码 < 100 行
- 纯 bug 修复，无架构变更
- 文档更新

**简化流程**:
```
Step 0 → Phase 0.5 (可选) → Phase 0.6 → Phase 1 → Phase 1.5 → Phase 6 → Phase 7
```

**要求**: Phase 0.6 和 Phase 1.5 必须执行，不能跳过

### L2 - 中等任务 (标准流程)
**判定标准** (满足任一):
- 修改文件 3-8 个
- 新增代码 100-500 行
- 新增接口或模块
- 影响现有功能

**标准流程**:
```
Step 0 → Phase 0.5 → Phase 0.6 → Phase 1 → Phase 1.5 → Phase 2-3 → Phase 6 → Phase 7
```

**注意**: Phase 0.6 和 Phase 1.5 必须执行

### L3 - 复杂任务 (完整流程)
**判定标准** (满足任一):
- 修改文件 > 8 个
- 新增代码 > 500 行
- 架构重构
- 涉及安全或性能关键路径

**完整流程**:
```
Step 0 → Phase 0.5 → Phase 0.6 → Phase 1 → Phase 1.5 → Phase 2 → Phase 3 → Phase 4 → Phase 5 → Phase 6 → Phase 7
```

## Phase 0.5: Design Doc (研究 & 设计)

**触发条件**: Step 0 评估为 L2/L3 | **适用级别**: 🔴 L2+ 必须，⚪ L1 可选

> **核心理念**: Design Doc 类似 DB Migrations — 每份文档记录一次重大设计决策的思考过程，
> 编号递增、提交进仓库，形成项目进化的完整脉络。

### 0.5.1 Design Doc 的价值

| 价值 | 说明 |
|-----|------|
| **思考留痕** | 记录调研过程、方案对比、决策理由，避免“为什么这样设计”的遗忘 |
| **可追溯性** | 编号递增 + Git 提交，任何时点可回溯设计决策 |
| **知识传承** | 新成员/新 AI 会话可通过 design-docs/ 快速理解项目演进 |
| **减少返工** | 先思考后编码，避免方向性错误导致大规模返工 |
| **评审依据** | Design Doc 是 Phase 0.6 方案审核确认的基础 |

### 0.5.2 文件命名规范

```
design-docs/
├── 001-mysql-cdc-architecture.md
├── 002-storage-layer-design.md
├── 003-retry-and-deadletter.md
└── README.md          ← 索引文件，自动维护
```

**命名规则**: `NNN-kebab-case-title.md`
- `NNN`: 三位数字，从 001 开始递增（类似 DB Migration 编号）
- `kebab-case-title`: 简短英文描述，kebab-case 格式
- 编号必须连续，不允许跳号

### 0.5.3 Design Doc 模板

```markdown
# Design Doc NNN: [标题]

## 元数据
- **编号**: NNN
- **标题**: [简短描述]
- **状态**: draft
- **创建日期**: YYYY-MM-DD
- **最后更新**: YYYY-MM-DD
- **关联任务**: [任务描述或 issue 编号]
- **复杂度级别**: L1 / L2 / L3
- **前置 Design Doc**: [如有关联，填写编号]

## 1. 背景与动机
- 为什么需要这个改动？
- 当前系统的痛点是什么？
- 业务/技术驱动因素

## 2. 调研与现状分析
### 2.1 现有实现
- 当前架构/代码如何工作
- 已有的限制和瓶颈

### 2.2 业界实践
- 同类系统的解决方案

## 方案变更审批流程 (NEW! v3.2+)

**触发条件**: 实现过程中发现原方案不可行，需要变更方案时

> **v3.2 新增**: 方案变更不能随意，必须经过审批流程

### 变更触发条件
- 原方案技术上不可行
- 用户需求发生变更
- 发现严重问题（性能、安全、兼容性）
- 实现复杂度远超预期

### 变更审批步骤
```
1. 暂停当前实现
  │
  ▼

  │
  ▼
3. 更新 Design Doc (如果是 L2/L3)
  │
  ▼
4. 重新进行 Phase 0.6: 方案审核确认
  │
  ▼
5. 用户重新确认方案选择
  │
  ▼
6. 更新 PLAN.md
  │
  ▼
7. 重新进行 Phase 1.5: Plan验证确认
  │
  ▼
8. 用户最终确认后继续执行
```

### 变更记录要求
- 变更时间
- 变更原因
- 新旧方案对比
- 用户确认记录

## 评审异常处理流程

当评审阶段未通过时，按以下流程处理：

```
评审结果
  │
  ├─ Phase 2 不通过
  │   ├─ 架构设计缺陷 → 修改设计方案 → 重新提交 Phase 2
  │   └─ 技术栈不合规 → 调整技术选型 → 重新提交 Phase 2
  │
  ├─ Phase 3 不通过
  │   ├─ 循环依赖 → 重构模块依赖 → 重新提交 Phase 3
  │   └─ 接口设计不合理 → 调整接口定义 → 重新提交 Phase 3
  │
  ├─ Phase 4 不通过
  │   ├─ 测试覆盖不足 → 补充测试用例 → 重新提交 Phase 4
  │   └─ 边界条件遗漏 → 补充边界处理 → 重新提交 Phase 4
  │
  ├─ Phase 5 不通过
  │   ├─ 安全漏洞 → 修复安全问题 → 重新提交 Phase 5
  │   └─ 敏感信息泄露 → 清理敏感数据 → 重新提交 Phase 5
  │
  └─ 连续 3 次不通过
      └─ 升级处理 → 召集相关人员讨论 → 更新 PLAN.md → 从 Phase 1 重新开始
```

### 异常处理原则

| 原则 | 说明 |
|-----|------|
| 小范围修复 | 仅修改不通过的部分，不扩大变更范围 |
| 记录原因 | 每次不通过必须记录原因和修改方案 |
| 限制重试 | 同一 Phase 连续 3 次不通过，升级处理 |
| 回溯检查 | 修改后需确认不影响已通过的 Phase |
