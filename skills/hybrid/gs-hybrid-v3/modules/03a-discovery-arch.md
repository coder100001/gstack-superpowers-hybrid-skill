# 03a — Decision Layer: IDEA → DISCOVERY → REQUIREMENT_LOCK → ARCH_REVIEW

> **Context Load**: 加载 `decision-layer/reviews/product-review.md`, `decision-layer/reviews/risk-review.md`（DISCOVERY 阶段）；`decision-layer/reviews/architecture-review.md`, `decision-layer/reviews/tradeoff-review.md`（ARCH_REVIEW 阶段）。

## 概述

本模块定义决策层的核心流程：从 IDEA 状态接收任务，经过 DISCOVERY 状态进行需求澄清，然后 REQUIREMENT_LOCK 进行需求确认，最后 ARCH_REVIEW 进行架构审议。

### 状态流程概览

```
┌─────────────────────────────────────────────────────────────────┐
│  DECISION LAYER (决策层)                                     │
└─────────────────────────────────────────────────────────────────┘
IDEA:       任务接收
DISCOVERY:  需求澄清 (Superpowers brainstorming - 渐进式提问)
             ↓ 产出：需求文档
REQUIREMENT_LOCK: 需求确认 (用户必须确认)
             ↓
ARCH_REVIEW: 多角色架构审议 (5 个维度独立投票)
             ↓ 产出：架构设计 + ADR
```

---

## DISCOVERY 状态：需求澄清

**触发条件**: L2+ 任务 (L1 可选)

**L1 快速通道**: L1 任务可将 DISCOVERY 与 REQUIREMENT_LOCK 合并为单次确认，不保存独立 spec 文件，直接口述确认后进入 TASK_DECOMPOSITION。

### 目标

先通过 brainstorming 方法论澄清需求、产出设计方案，然后保存为 spec 文件。

### Step 0: Announce at Start

在需求澄清开始时，必须声明：

> "我将按照 AI Engineering Governance System (v4.0) 三层架构执行。现在进入 DISCOVERY 状态，使用 brainstorming 方法论进行需求澄清。我会先探索项目上下文，然后通过渐进式提问理解需求，最后提出设计方案供你审查。"

### Step 1: 探索项目上下文

在任何提问之前，必须先理解项目现状：
- 检查项目目录结构、关键配置文件
- 阅读相关代码文件（了解现有架构和数据流）
- 检查最近的 git 提交记录
- 了解当前的技术栈和约束

### Step 2: 范围评估与子系统拆解

在开始渐进式提问之前，判断需求规模。**此阶段漏检多子系统将导致后续状态回退，浪费设计文档和方案确认的工作。**

**多子系统判定标准** (满足任意 2 项即为多子系统):

| 维度 | 判定标准 |
|------|---------|
| **独立数据模型** | 有独立的数据库表/实体集合，可独立 CRUD |
| **独立用户界面** | 有独立的页面/路由/入口点 |
| **独立部署单元** | 可独立部署、独立扩缩容、独立监控 |
| **独立用户角色** | 不同子系统由不同角色使用 |
| **独立外部依赖** | 依赖不同的第三方服务或 API |

**处理规则**:
- 满足任意 2 项 → **立即标记为多子系统**
- 与用户确认拆解方案：每个子系统独立走 DISCOVERY → REQUIREMENT_LOCK → ARCH_REVIEW 周期
- 子系统之间通过明确接口契约通信，在各自的 spec/plan 中只定义接口、不实现对方

**单一子系统判定**: 所有功能围绕同一个核心数据模型/业务流程，即使涉及多个文件也视为单一子系统。

### Step 3: 渐进式需求澄清

**核心原则** (来自 brainstorming 方法论):

| 原则 | 说明 |
|------|------|
| 一次只问一个问题 | 不堆砌问题，避免用户被淹没 |
| 优先选择题 | 给 2-4 个选项降低用户回答成本；开放问题也可以 |
| 一条消息一个问题 | 话题需要深入时拆成多个问题 |
| 必要时回溯澄清 | 如果发现矛盾或模糊，返回确认 |
| 聚焦目的/约束/成功标准 | 理解 what & why，而不是 how |

**澄清维度参考** (按优先级递进，不是强制清单):

| 轮次 | 维度 | 说明 |
|:----:|------|------|
| 1 | **目的与痛点** | 这个功能的核心目标是什么？解决什么具体痛点？ |
| 2 | **用户与角色** | 谁会使用？有几种角色？每种角色有什么不同需求？ |
| 3 | **约束条件** | 技术栈限制？兼容性要求？时间/资源约束？ |
| 4 | **成功标准** | 怎么判断做好了？有具体可衡量指标吗？ |
| 5 | **边界与范围** | 有什么明确不做的事情？范围的硬边界在哪里？ |
| 6 | **风险识别** | 有哪些你担心的潜在问题或不确定性？ |

**注意**: 以上是参考维度而非强制清单。根据实际对话灵活调整，目标是真正理解需求，不是跑完清单。

**涉及视觉的问题**: 当需要澄清任何可见的事物（UI 布局、组件外观、交互形态）时，可使用浏览器工具展示参考或原型帮助沟通。

### Step 4: 方案探索

理解需求后，提出 2-3 个可选方案：
- 以对话方式呈现，带利弊分析
- 先给出推荐方案及理由
- 解释为什么推荐这个方案

### Step 5: 设计呈现

确认方案方向后，呈现具体设计：
- 按章节逐步呈现，每个章节后确认是否正确
- 覆盖：架构、组件/模块、数据流、错误处理、测试策略
- 愿意回溯澄清，如果某些部分不合理

### 设计隔离性原则

对每个设计单元，回答三个问题：
1. 它做什么？（单一清晰目的）
2. 怎么使用它？（良好定义的接口）
3. 它依赖什么？（明确的依赖边界）

小文件是好的信号——当文件变大时，通常意味着它承担了太多职责。

### 已有代码库的特殊处理

- 先探索当前代码结构，再提出变更
- 遵循现有模式
- 如果已有代码存在问题影响当前工作（如文件太大、边界不清、职责混乱），在设计中有针对性地改进
- 不要提出无关的重构——聚焦于服务于当前目标

### Step 6: 反模式警告

| 反模式 | 为什么是问题 |
|--------|-------------|
| **"太简单不需要设计"** | 最简单项目的未检验假设浪费最多工作。设计可以很短（简单项目几句话），但必须呈现并获批准 |
| **跳过上下文探索** | 不理解项目现状的提问是盲目的 |
| **一次性堆砌问题** | 用户被淹没，回答质量下降 |
| **假设需求** | 没有确认过的假设 = 潜在的返工 |
| **只提一个方案** | 没有对比就没有真正的选择 |

### Step 7: 保存 Spec 文件并过渡到 REQUIREMENT_LOCK

用户确认设计后：
1. 将确认的设计保存为 spec 文件到 `context-layer/specs/YYYY-MM-DD-<feature>-spec.md`
2. 让用户审查 spec 文件
3. 用户批准 spec 后，进入 REQUIREMENT_LOCK 状态

**过渡协议**: 需求澄清完成后，只应建议进入 REQUIREMENT_LOCK 状态，不直接跳转到编码实现。

---

## REQUIREMENT_LOCK 状态：需求确认

**前置**: DISCOVERY 状态的 spec 文件已保存并获用户批准（L1 快速通道除外）。

**触发条件**: 所有级别任务 (L1/L2/L3)

<HARD-GATE>
**这是强制阻断点！** 用户必须明确确认需求范围，否则不能进入 ARCH_REVIEW。

**L1 快速通道规则**: L1 任务可将此确认与 DISCOVERY 合并为单次对话完成，不强制保存独立 spec 文件，但必须在对话中明确获得用户确认。
</HARD-GATE>

### 目标

在需求澄清后、架构审议前，确保用户对需求有充分理解并明确确认。

### 必须展示的内容

1. **需求清单**
   - 功能需求
   - 非功能需求
   - 范围边界
   - 成功标准

2. **用户确认**
   - 等待用户明确回复
   - 不能默认选择
   - 不能跳过

### 确认对话模板（L2/L3 标准版）

```
AI: 基于 DISCOVERY 阶段完成，我整理了以下需求清单，请确认：

【需求清单】
- 功能需求：...
- 非功能需求：...
- 范围边界：...
- 成功标准：...

请确认：
1. 您是否同意以上需求范围？
2. 或者有需要补充或修改的部分？

[等待用户明确回复]
```

### 确认对话模板（L1 快速版）

```
AI: 确认一下需求：
- 目标：[一句话]
- 范围：[边界]
- 验收：[标准]

如确认无误，我将直接开始任务拆解。请回复"确认"。
```

### 阻断规则

- ❌ 用户未回复 → 等待
- ❌ 用户回复模糊 → 追问澄清
- ❌ 用户需要修改 → 退回 DISCOVERY 状态
- ✅ 用户明确确认 → 进入 ARCH_REVIEW 状态（L1 无架构变更时可跳过 ARCH_REVIEW 直接进入 TASK_DECOMPOSITION）

### 输出要求

必须记录：
- 用户确认的需求清单
- 确认时间
- 相关修改记录（如有）
- **L1 快速通道**: 在对话中记录即可，不强制文件化

## ARCH_REVIEW 状态：架构审议

**前置**: REQUIREMENT_LOCK 状态已完成。

### 目标

在需求确认后、任务拆解前，进行多角色架构审议，确保方案的可行性和质量。

### 架构审议维度

参考 [decision-layer/reviews/architecture-review.md](../../../../decision-layer/reviews/architecture-review.md)

**审议维度按复杂度分级**：

| 级别 | 启用维度 | 说明 |
|------|---------|------|
| L1 | 跳过 | 无架构变更时不触发 ARCH_REVIEW |
| L2 | Product + Architect | 2 维度审议，聚焦业务价值与技术可行性 |
| L3 | 全 5 维度 | Product + Architect + Performance + Security + Operations |

**5 个维度定义**（L3 全量，L2 仅用前 2 项）：

| 维度 | 审议重点 |
|------|---------|
| Product Reviewer | 业务价值、用户影响、范围合理性、ROI |
| System Architect | 模块划分、依赖方向、技术选型 |
| Performance Reviewer | 吞吐、延迟、缓存、瓶颈 |
| Security Reviewer | 信任边界、数据暴露、权限 |
| Operations Reviewer | 部署、回滚、监控、迁移成本 |

### 架构设计文档编写

**前置**: REQUIREMENT_LOCK 状态已完成。

> 架构设计文档类似 DB Migrations — 记录重大架构决策的思考过程。spec 回答 "what"，架构设计文档回答 "how and why"。

#### Spec 自审查

编写架构设计文档前，AI 必须自审查：

1. **占位符扫描**: 有没有 "TBD"、"TODO"、不完整的部分？模糊的需求？→ 修复
2. **内部一致性**: 各章节是否矛盾？架构描述是否与功能描述一致？
3. **范围检查**: 是否聚焦在单个实现计划内？还是需要进一步拆解？
4. **歧义检查**: 任何需求是否可被两种方式解读？若是，选一个并显式化

发现问题 → 立即修复 → 无需重复审查。

#### 方案调研

**调研维度**:
- 业界最佳实践
- 类似项目的实现方式
- 技术选型的优缺点
- 潜在的坑和解决方案

#### 方案对比

**必须对比至少 2-3 个方案**:

| 方案 | 优点 | 缺点 | 适用场景 | 复杂度 |
|------|------|------|---------|--------|
| A | ... | ... | ... | L? |
| B | ... | ... | ... | L? |
| C | ... | ... | ... | L? |

#### 设计决策

**决策依据**:
- 为什么选这个方案？
- 放弃了什么？为什么？
- 未来的扩展性如何？
- 维护成本如何？

### 方案审核确认

**触发条件**: 所有级别任务 (L1/L2/L3)

<HARD-GATE>
**这是强制阻断点！** 用户必须明确确认方案选择，AI 才能继续。
</HARD-GATE>

### 必须展示的内容

1. **方案对比表格**
   - 至少 2-3 个可选方案
   - 清晰的优缺点对比
   - 复杂度评估

2. **AI 推荐方案**
   - 明确推荐哪个方案
   - 详细的推荐理由
   - 风险提示

3. **用户确认**
   - 等待用户明确回复
   - 不能默认选择
   - 不能跳过

### 确认对话模板

```
AI: 基于需求分析，我提出了以下方案：

【方案对比表】
...

我推荐采用【方案 X】，理由：
1. ...
2. ...

⚠️ 风险提示：...

请确认：
1. 您是否同意选择【方案 X】？
2. 或者您倾向于其他方案？
3. 是否有其他考虑因素？

[等待用户明确回复]
```

### 阻断规则

- ❌ 用户未回复 → 等待
- ❌ 用户回复模糊 → 追问澄清
- ❌ 用户选择不同方案 → 重新评估影响
- ✅ 用户明确确认 → 进入 TASK_DECOMPOSITION 状态

### 输出要求

必须记录：
- 用户选择的方案
- 选择理由
- 确认时间
- 相关风险接受声明
- 架构设计文档路径
- ADR (Architecture Decision Record) 记录
