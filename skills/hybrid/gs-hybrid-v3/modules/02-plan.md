# 02 — PLAN: 方案设计 + 任务拆解 + 确认

> 加载时机: DEFINE→PLAN 跃迁后。结束前 user 确认计划方能进 IMPLEMENT。

## 架构评审

L2: 2 维度评审（Product + Architect）。L3: 5 维度（+Security+Operations+DX）。

评审重点:
- 方案对比（≥ 2 方案）及选择理由
- 技术选型 trade-off
- API/数据结构变更影响
- 性能/安全性考量

产出 ADR（架构决策记录），格式自定，包含: 标题、状态、日期、背景、决策、后果。

## 任务拆解

把需求分解为可执行的 task:

### 拆解方法

1. **输入**: spec 文件（需求清单 + 验收标准 + 边界条件）
2. **功能点提取**: 每条 REQ/NFR 编号对应一个或多个功能点
3. **排序**: 按依赖关系拓扑排序（输出依赖图）
4. **task 拆分粒度**: 每个 task 可独立提交、独立测试。典型粒度 1-5 文件、30-100 行
5. **每个 task 包含**:
   - 文件路径（精确到文件级）
   - 改动范围（新增/修改/删除）
   - 验收标准（来自 spec 的验收标准编号）
   - 测试要求（单元/集成/E2E）
   - 预估工时
6. **跨切面识别**: 日志、监控、权限、国际化——统一在顶层处理，不分散到每个 task

### 验收标准映射

每个 task 的验收标准直接对应 spec 中的 `AC-*` 编号:
```
Task 1: 实现用户登录接口
  AC-001: 输入正确凭据返回 token
  AC-002: 输入错误密码返回 401
  AC-003: 连续 5 次失败锁定账户 15 分钟
```

### Task 类型分类

| 类型 | 说明 | 典型规模 |
|------|------|---------|
| 数据层 | 数据模型、存储逻辑 | 1-2 文件 |
| 业务层 | 核心业务逻辑 | 2-5 文件 |
| 接口层 | API/Controller | 1-3 文件 |
| 测试 | 测试用例 | 2-5 文件 |
| 配置/部署 | 非功能变更 | 1 文件 |

### 依赖图规则

- 数据层 → 业务层 → 接口层（单向）
- 测试依赖对应的实现 task
- 无循环依赖（若有，拆分为独立模块）

## 计划确认

PLAN→IMPLEMENT 跃迁要求:

1. 完整 ADR（L2 简要，L3 完整）
2. 拆解后的 task 清单 + 依赖图
3. **用户确认执行计划**（对话确认）
4. L0/L1 简化: L0 无计划，L1 仅 task 清单 + 一次确认
