# Tradeoff Deliberation Protocol

> **层**: Decision Layer · **职责**: 多方案权衡与技术选型多维度审议
> **触发条件**: L2+ 任务、存在多个可选方案、用户要求选型评审
> **前置状态**: REQUIREMENT_LOCK · **后置状态**: TASK_DECOMPOSITION

---

## 1. 参与者

每次权衡审议必须包含以下五个决策维度。每个维度代表一个独立的关注点，而非角色扮演。

| 维度 | 审议重点 | 否决权 |
|:-----|:---------|:-------|
| **Tech Evaluator** | 技术成熟度、技术栈匹配、学习曲线、社区支持 | 可否决技术风险过高的方案 |
| **Cost Analyst** | 开发成本、运维成本、许可费用、长期成本 | 可否决成本过高的方案 |
| **Time Assessor** | 开发时间、学习时间、迁移时间、交付周期 | 可否决时间不允许的方案 |
| **Risk Assessor** | 风险对比、不确定性、可维护性、可扩展性 | 可否决风险过大的方案 |
| **Future Proof** | 演进能力、技术债务、 vendor lock-in、生态系统 | 可否决缺乏未来性的方案 |

## 2. 审议流程

### 2.1 前置输入

在开始审议前，必须加载以下上下文：
- 已确认的需求文档（来自 DISCOVERY 阶段）
- 所有可选方案的详细描述
- 架构约束条件
- 项目约束契约（project-spec）
- 技术选型历史

### 2.2 审议步骤

```
Step 1: 方案展示（每个方案 3 分钟）
  └─ 依次展示所有可选方案，包括核心思路、优缺点

Step 2: 多维度对比（15-20 分钟）
  ├─ 建立对比矩阵
  ├─ 每个维度独立评分
  └─ 识别关键权衡点

Step 3: 敏感性分析（10分钟）
  ├─ 哪些假设最重要？
  ├─ 假设变化时结论如何变化？
  └─ 最坏情况下的表现

Step 4: 偏好澄清（5分钟）
  ├─ 哪些约束是硬约束？
  ├─ 哪些是软约束？
  └─ 优先级排序

Step 5: 决策表决
  ├─ Selected: 选中某个方案，进入 TASK_DECOMPOSITION
  ├─ Hybrid: 组合多个方案的优点
  └─ Defer: 需要更多信息或原型验证
```

### 2.3 审议规则

- 必须至少有 2 个可选方案才能进行权衡审议
- 每个方案必须明确列出优缺点
- 必须使用统一的评分标准
- 硬约束必须满足，软约束可权衡
- "Selected" 要求有明确的胜出方案
- "Hybrid" 要求组合方案的可行性经过验证
- "Defer" 要求明确需要补充的信息或验证方法
- 审议期间禁止预先设定结论

## 3. 必讨论项

### 3.1 技术对比 (Technical Comparison)
- 技术成熟度对比？
- 性能对比（吞吐量/延迟/资源消耗）？
- 可扩展性对比？
- 可维护性对比？
- 与现有技术栈的匹配度？
- 学习曲线对比？
- 社区活跃度与生态系统？

### 3.2 成本对比 (Cost Comparison)
- 开发成本对比（人天/人月）？
- 运维成本对比？
- 许可费用对比？
- 长期总成本对比？
- 成本增长曲线对比？
- 机会成本对比？

### 3.3 时间对比 (Time Comparison)
- 开发时间对比？
- 学习时间对比？
- 迁移时间对比？
- 交付周期对比？
- 时间风险对比？

### 3.4 风险对比 (Risk Comparison)
- 技术风险对比？
- 供应商锁定风险对比？
- 项目风险对比？
- 安全风险对比？
- 风险缓解难度对比？

### 3.5 未来性对比 (Future-proofing)
- 技术演进能力对比？
- 技术债务对比？
- 生态系统发展趋势？
- 退出成本对比？
- 标准化程度对比？

### 3.6 折中分析 (Tradeoff Analysis)
- 哪些是必须放弃的？
- 哪些是必须坚持的？
- 有没有第三条路？
- 各方案的核心优势是什么？
- 各方案的致命缺陷是什么？

### 3.7 验证策略 (Validation Strategy)
- 是否需要做 POC？
- 是否需要做性能测试？
- 是否需要做安全审计？
- 验证的时间和成本？
- 验证的成功标准？

## 4. 输出工件

审议完成后必须产出的工件：

```
1. Tradeoff Decision Record (TDR)
   ├─ 标题: [日期] <选型决策名称>
   ├─ 状态: Approved | Deprecated | Superseded
   ├─ 背景: 需要选型的问题
   ├─ 可选方案: 所有考虑过的方案列表
   ├─ 对比矩阵: 多维度对比表格
   ├─ 决策依据: 为什么选择这个方案
   ├─ 关键权衡: 做出了哪些妥协
   ├─ 被否决方案: 为什么否决其他方案
   └─ 未来演进: 未来可能的调整方向

2. 对比矩阵 (Comparison Matrix)
   ├─ 评估维度: 技术/成本/时间/风险/未来性
   ├─ 权重: 各维度的重要性权重
   ├─ 方案A评分: 每个维度的评分
   ├─ 方案B评分: 每个维度的评分
   ├─ ...: 其他方案的评分
   └─ 加权总分: 各方案的加权总分

3. 审议结论摘要
   ├─ 决策: Selected / Hybrid / Defer
   ├─ 选中方案: 最终选择的方案
   ├─ 决策理由: 核心决策依据
   ├─ 关键权衡: 主要的妥协点
   ├─ 验证计划: (Defer 时) 验证方案
   └─ 未解决争议: 需要进一步讨论的事项
```

---

## 5. 红线规则

审议过程中的禁止行为：
- 只有一个方案就进行审议 —— 必须有至少两个可选方案
- 预先设定结论 —— 必须保持客观
- 忽略某个评估维度 —— 五个维度缺一不可
- 用"个人偏好"替代数据 —— 决策必须有依据
- 审议未完成即开始实施 —— 这是状态机违规
- 口头共识替代书面 TDR —— 所有选型决策必须有记录
