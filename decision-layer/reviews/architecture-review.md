# Architecture Deliberation Protocol

> **层**: Decision Layer · **职责**: 多维度架构审议
> **触发条件**: L2+ 任务、涉及架构变更、用户要求评审
> **前置状态**: REQUIREMENT_LOCK · **后置状态**: TASK_DECOMPOSITION

---

## 重要说明

> **AI 是分析引擎，不是角色扮演者。**
> 
> 本协议定义的是**审议维度**（Review Dimensions），而非角色。AI 应按维度输出事实和风险评估，禁止生成任何模拟角色对话的内容。

---

## 1. 审议维度

每次架构审议必须包含以下五个决策维度。每个维度代表一个独立的关注点。

| 维度 | 审议重点 | 否决条件 |
|:-----|:---------|:---------|
| **Product 维度** | 业务价值对齐、用户影响范围、需求覆盖完整性、ROI 合理性 | 与产品目标冲突的方案 |
| **Architect 维度** | 模块划分清晰度、依赖方向正确性、技术选型合理性、接口契约完整性 | 违反架构原则的方案 |
| **Performance 维度** | 吞吐量预估、延迟预算、缓存策略、潜在瓶颈、资源消耗 | 不满足性能约束的方案 |
| **Security 维度** | 信任边界定义、数据暴露面、认证授权模型、敏感信息处理 | 存在安全风险的方案 |
| **Operations 维度** | 部署复杂度、回滚可行性、监控覆盖、迁移成本、依赖可用性 | 不可运维的方案 |

### 分级审议规则

> **复杂度分级**: L1/L2/L3 的判定标准以 [02-complexity.md](../../skills/hybrid/gs-hybrid-v3/modules/02-complexity.md) 为唯一真相源。本节定义审议维度激活规则。

不同复杂度级别激活不同维度集合：

| 级别 | 必须维度 | 可选维度 | 说明 |
|:-----|:---------|:---------|:-----|
| **L1** | Product, Architect | — | 快速审议，2 维度即可 |
| **L2** | Product, Architect, Performance | Security, Operations | 3 维度必须，涉及安全/运维时激活对应维度 |
| **L3** | 全部 5 维度 | — | 全维度审议，缺一不可 |

> **激活判定**: 如果 L2 任务涉及用户数据、外部 API、或部署变更，则 Security 和 Operations 维度自动升级为必须。

## 2. 审议流程

### 2.1 前置输入

在开始审议前，必须加载以下上下文：
- 已确认的需求文档（来自 DISCOVERY 阶段）
- 项目约束契约（project-spec）
- 活跃的 ADR 历史
- 变更范围边界

### 2.2 审议步骤

```
Step 1: 方案陈述
  └─ 陈述设计方案，包括架构图、模块划分、数据流

Step 2: 各维度评估（每维度独立输出）
  ├─ Product 维度: 这个方案解决的是否是正确的问题？
  ├─ Architect 维度: 模块边界是否合理？是否存在循环依赖？
  ├─ Performance 维度: 是否存在性能瓶颈？缓存策略是什么？
  ├─ Security 维度: 信任边界在哪里？数据如何保护？
  └─ Operations 维度: 如何部署？如何回滚？如何监控？

Step 3: 风险登记
  └─ 每个维度输出识别的风险与严重等级（Critical/Major/Minor）

Step 4: 决策表决
  ├─ Approved: 方案通过，进入 TASK_DECOMPOSITION
  ├─ Conditional: 方案有条件通过，需解决标注的风险点
  └─ Rejected: 方案被否决，需重新设计
```

### 2.3 审议规则

- 每个维度独立输出结论，不可互相替代
- "Approved" 要求所有维度无 Critical 级别风险
- "Conditional" 要求所有维度无架构性异议，仅存在可修复的具体问题
- "Rejected" 任一维度投出否决票即触发
- 审议期间禁止讨论实现细节

## 3. 必讨论项

### 3.1 可扩展性 (Scalability)
- 系统能否水平扩展？
- 哪些组件会成为瓶颈？
- 数据量增长 10x/100x 时架构是否仍然成立？

### 3.2 故障恢复 (Failure Recovery)
- 单点故障在哪里？
- 降级策略是什么？
- 数据一致性如何在故障时保证？

### 3.3 迁移影响 (Migration Impact)
- 现有系统如何平滑迁移？
- 是否需要数据迁移？迁移方案是什么？
- 回滚路径是否清晰？

### 3.4 兼容性 (Compatibility)
- 向后兼容策略是什么？
- API 版本化方案？
- 与外部系统的接口兼容性？

### 3.5 数据一致性 (Data Consistency)
- 最终一致性还是强一致性？
- 分布式事务方案？
- 数据冲突解决策略？

### 3.6 基础设施成本 (Infra Cost)
- 资源预估（计算/存储/带宽）
- 成本增长曲线
- 是否有更经济的替代方案？

### 3.7 可观测性 (Observability)
- 日志、指标、追踪的覆盖范围
- 关键告警阈值
- 排障路径是否清晰？

## 4. 输出工件

审议完成后必须产出的工件：

```
1. Architecture Decision Record (ADR)
   ├─ 标题: [日期] <架构决策名称>
   ├─ 状态: Approved | Deprecated | Superseded
   ├─ 背景: 需要决策的问题
   ├─ 方案: 选中的方案描述
   ├─ 被否决方案: 替代方案及否决理由
   ├─ 风险: 已识别的风险及缓解措施
   └─ 回滚策略: 如何回退此决策

2. 审议结论摘要
   ├─ 决策: Approved / Conditional / Rejected
   ├─ 批准条件: (Conditional 时) 需满足的具体条件
   ├─ 风险登记表: 所有维度的风险记录
   └─ 未解决争议: 需要进一步讨论的事项
```

---

## 5. 红线规则

审议过程中的禁止行为：
- 讨论具体代码实现 —— 这是执行层的职责
- 跳过当前级别必须的审议维度 —— L1 至少 2 维度，L2 至少 3 维度，L3 全 5 维度
- 用"先做再优化"绕过否决 —— 架构问题必须在审议阶段解决
- 审议未完成即开始编码 —— 这是状态机违规
- 口头共识替代书面 ADR —— 所有决策必须有记录
